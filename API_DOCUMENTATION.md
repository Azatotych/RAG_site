# API документация проекта RAG_site

## 1. Область документа

Этот документ описывает **фактический API-контракт frontend-приложения** (`React + Vite`) из текущего кода проекта.

Важно:
- в репозитории реализован frontend;
- backend в этом проекте отсутствует;
- ниже описано, **какие запросы frontend отправляет и чего ожидает** от backend.

---

## 2. Где и как работают чаты

## 2.1. Структура чатов на клиенте

Чаты хранятся в состоянии `App.tsx`:

- `chats: Array<{ id, title, updatedAt }>` — список чатов для сайдбара;
- `activeChatId: string` — текущий активный чат;
- `messagesByChat: Record<chatId, { rag: ChatMessage[]; chat: ChatMessage[] }>` — сообщения по каждому чату и режиму;
- `placeholdersByChat: Record<chatId, string>` — плейсхолдеры для поля ввода.

Ключевой момент: у каждого чата **две отдельные ветки истории**:
- `chat` (обычный режим),
- `rag` (режим с источниками).

Переключение режима меняет активную ветку сообщений внутри того же чата.

## 2.2. Где хранятся чаты

Чаты хранятся:
- в `React state` во время сессии;
- в `localStorage` для восстановления после перезагрузки страницы.

Ключ `localStorage`:
- `vas-chats-v1`

Отдельно тема интерфейса хранится в ключе:
- `vas-theme`

## 2.3. Как работает сохранение чатов

Сохранение работает автоматически:
- при отправке сообщения добавляется `user`-сообщение и временное `assistant`-сообщение;
- по мере ответа backend `assistant`-сообщение заполняется;
- `updatedAt` для активного чата проставляется строкой `"только что"`.

После любого изменения чатов frontend сериализует в `localStorage`:
- `chats`;
- `activeChatId`;
- `placeholdersByChat`;
- `messagesByChat` (отдельно по режимам `chat`/`rag`).

При старте приложения данные читаются из `localStorage` и валидируются:
- некорректные структуры игнорируются;
- при поврежденном/пустом состоянии создается новый чат по умолчанию;
- если `activeChatId` невалиден, выбирается первый доступный чат.

Операции над чатами:
- создание нового чата: локально генерируется `id` (`crypto.randomUUID`);
- переименование: только локальное изменение `title`;
- удаление:
  - если чат один — история очищается, чат остается;
  - если чатов несколько — чат удаляется из локального состояния;
- очистка чата (`Очистить чат`) очищает **только сообщения текущего режима** (`chat` или `rag`) в активном чате.

## 3. Переменные окружения API

Используются переменные:

- `VITE_API_BASE_URL`
- `VITE_CHAT_ENDPOINT`
- `VITE_DOCUMENTS_ENDPOINT`
- `VITE_UPLOAD_ENDPOINT`
- `VITE_MODELS_ENDPOINT`

Сборка URL (`buildRequestUrl`):
- если endpoint абсолютный (`http://` или `https://`) — используется как есть;
- иначе склеивается с `VITE_API_BASE_URL`;
- если endpoint пустой — запрос не отправляется, в UI показывается ошибка конфигурации.

Рекомендуемые значения (из `.env.example`):

```env
VITE_API_BASE_URL=http://localhost:8080
VITE_CHAT_ENDPOINT=/api/chat
VITE_DOCUMENTS_ENDPOINT=/api/documents
VITE_UPLOAD_ENDPOINT=/api/documents/upload
VITE_MODELS_ENDPOINT=/api/models
```

## 4. API обращения frontend

## 4.1. GET /api/models

Назначение:
- загрузка моделей для селектора в левом сайдбаре.

Когда вызывается:
- при старте приложения (в `useEffect`).

Параметры:
- метод: `GET`;
- тело: отсутствует;
- timeout: `10 секунд` (AbortController).

Ожидаемые форматы ответа:

1) объект:
```json
{
  "models": [
    { "id": "qwen2.5", "label": "Qwen 2.5" }
  ]
}
```

2) массив:
```json
["qwen2.5", "llama3.1"]
```

3) альтернативно объект с `items`.

Нормализация:
- поддерживаются поля `id | model | name` для идентификатора;
- `label | name | title | id | model` для подписи;
- дубликаты по `id` отфильтровываются.

Поведение селектора:
- если ранее выбранная модель присутствует в новом списке — выбор сохраняется;
- иначе выбирается первая модель из ответа;
- если список пуст/ошибка — селектор показывает недоступность и ошибка выводится в UI.

## 4.2. GET /api/documents

Назначение:
- загрузка списка документов для RAG-источников.

Когда вызывается:
- при старте приложения;
- после успешного upload;
- по кнопке «Обновить».

Параметры:
- метод: `GET`;
- тело: отсутствует;
- timeout: `10 секунд`.

Ожидаемые форматы:

1) объект:
```json
{
  "documents": [
    { "id": "report", "name": "report.pdf", "path": "docs/report.pdf" }
  ]
}
```

2) объект с `items`;

3) массив строк:
```json
["docs/report.pdf", "docs/manual.docx"]
```

Нормализация:
- для строки `docs/a.pdf`:
  - `id = "docs/a.pdf"`,
  - `name = "a.pdf"`,
  - `path = "docs/a.pdf"`;
- для объекта:
  - `id` берется из `id`, либо fallback в `path`, `name`, `document-N`;
  - `name` берется из `name/title/filename` либо из конца `path`.
- дубликаты по `id` удаляются.

Особенности:
- после перезагрузки списка выбранные документы сохраняются только если их `id` все еще присутствуют в новом ответе;
- при ошибке список очищается и выводится сообщение в панели источников.

## 4.3. POST /api/documents/upload

Назначение:
- загрузка документов через UI (кнопка «Загрузить»/«Файл»).

Параметры:
- метод: `POST`;
- `Content-Type`: `multipart/form-data` (автоматически браузером);
- поле формы: `files` (множественное, каждый файл append в `FormData`);
- timeout: `10 минут` (`600000 ms`).

Допустимые расширения на уровне input:
- `.pdf`, `.docx`, `.txt`, `.md`

Важно:
- ограничение по расширениям клиентское; backend должен валидировать тип/размер/безопасность отдельно.

Успех:
- после успешного ответа frontend заново вызывает `GET /api/documents`.

Ошибка:
- в UI показывается `HTTP status + statusText + response.text()` (если есть).

## 4.4. POST /api/chat

Назначение:
- отправка сообщений в модель (обычный чат или RAG).

Когда вызывается:
- отправка формы/Enter в поле ввода.

Параметры:
- метод: `POST`;
- заголовок: `Content-Type: application/json`;
- timeout: `10 минут`.

Тело запроса:
```json
{
  "messages": [
    { "role": "user", "content": "..." },
    { "role": "assistant", "content": "..." }
  ],
  "stream": true,
  "mode": "rag",
  "sources": ["doc-1", "doc-2"],
  "model": "qwen2.5"
}
```

Правила формирования:
- `messages`:
  - берется история текущего чата и текущего режима;
  - сообщения `role: "error"` в backend **не отправляются**;
- `stream` всегда отправляется как `true`;
- `mode` всегда отправляется (`chat` или `rag`);
- `sources`:
  - в `rag` отправляются выбранные `id` документов;
  - в `chat` отправляется пустой массив `[]`;
- `model` отправляется только если пользователь выбрал модель.

Ограничение отправки на клиенте (`canSend`):
- текст не пустой;
- нет активной отправки;
- для режима `rag` должен быть выбран минимум 1 документ.

Примечание:
- в текущем frontend нет верхнего лимита на количество выбранных `sources`; лимит рекомендуется проверять на backend.

## 5. Обработка ответа /api/chat

Frontend поддерживает 2 формата ответа:

## 5.1. JSON-ответ

Если `Content-Type` содержит `application/json`, ожидается:

```json
{ "reply": "текст ответа" }
```

Если `reply` отсутствует, выводится ошибка: `JSON без поля reply`.

## 5.2. Потоковый текст

Если ответ не JSON и присутствует `response.body`, frontend:
- читает поток `ReadableStream` через `getReader()`;
- декодирует чанки `TextDecoder('utf-8')`;
- постепенно обновляет текст assistant-сообщения.

Важно:
- это чтение «сырого» текстового потока;
- специальный SSE-протокол (`data:` события) отдельно не парсится.

## 6. Селектор моделей: полное поведение

1. При старте выполняется `GET /api/models`.
2. Пока идет загрузка, UI показывает `Загрузка моделей...`.
3. При успешном ответе:
   - данные нормализуются;
   - выбирается существующая текущая модель или первая из списка.
4. При ошибке:
   - список моделей очищается;
   - `selectedModel` сбрасывается;
   - в UI отображается причина.
5. При отправке чата:
   - если `selectedModel` не пустой, добавляется поле `"model"` в `POST /api/chat`.

---

## 7. Загрузка документов: полное поведение

1. При старте выполняется `GET /api/documents`.
2. В RAG-панели доступны:
   - поиск по имени документа (фильтрация только на клиенте),
   - «Выбрать все»,
   - «Снять выбор»,
   - чекбоксы по документам.
3. Выбранные документы передаются в `sources` при `POST /api/chat` в режиме `rag`.
4. Upload файлов:
   - отправка `multipart/form-data` с `files`;
   - после успеха — автоперезагрузка списка документов.

---

## 8. Ошибки и таймауты

Таймауты:
- `GET /api/models` — 10с;
- `GET /api/documents` — 10с;
- `POST /api/documents/upload` — 10мин;
- `POST /api/chat` — 10мин.

Обработка ошибок:
- `AbortError` → `превышено время ожидания`;
- сетевые ошибки `failed to fetch`/DNS → человекочитаемое сообщение;
- HTTP-ошибки показываются с кодом и статусом;
- для чата ошибки отображаются как отдельное сообщение `role: error` в ленте.

---

## 9. Что backend должен гарантировать для стабильной работы UI

Минимальные ожидания frontend:

- `GET /api/models` возвращает список моделей в одном из поддерживаемых форматов;
- `GET /api/documents` возвращает стабильные `id` документов;
- `POST /api/documents/upload` принимает `files` как multipart-поле;
- `POST /api/chat` принимает `messages`, `mode`, `sources`, опциональный `model`;
- `POST /api/chat` возвращает:
  - либо JSON `{ "reply": "..." }`,
  - либо обычный текстовый stream.

Рекомендации:
- не менять имена основных полей без версионирования API;
- валидировать `sources` и `model` на backend;
- ограничивать размер/тип загружаемых файлов на backend независимо от frontend.

---

## 10. Краткий чек-лист API

1. `GET /api/models` — список моделей для селектора.
2. `GET /api/documents` — список документов-источников.
3. `POST /api/documents/upload` — загрузка файлов (`files`).
4. `POST /api/chat` — чат/раг запрос и ответ (JSON `reply` или stream).

## 11. Обработка формул в ответах модели

Frontend поддерживает математический рендеринг через `remark-math + rehype-katex`.

Что добавлено:
- подключены KaTeX-стили;
- markdown-ответ ассистента проходит предобработку `normalizeAssistantMath`;
- выражения вида `( ... )`, похожие на математические/LaTeX-формулы, автоматически конвертируются в math-нотацию и рендерятся как формулы.

Примеры форматов, которые теперь корректно отображаются:
- `( x^{m/n} = \sqrt[n]{x^m} )`
- `( e^{ix} = \cos(x) + i\sin(x) )`
- `( \int_{a}^{b} f(x),dx = F(b) - F(a) )`
- `( \lim_{x \to 0} \frac{\sin(x)}{x} = 1 )`

Замечание:
- обычный markdown (списки, ссылки, код) сохраняет прежнее поведение;
- если текст в скобках не похож на формулу, он остается обычным текстом.
